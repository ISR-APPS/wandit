# AI error normalization, observability, and admin conversation inspector (final design)

Date: 2026-08-25. This document replaces design v2 (2026-08-25) and design v1 (2026-08-24).

Stack facts: `ai@7.0.19`, `@ai-sdk/gateway@4.0.15`, `@ai-sdk/mcp@2.0.10`, `@openrouter/ai-sdk-provider@3.0.0`, `@sentry/nestjs@10.69.0`, `posthog-node@5.28.0` (`node_modules/.pnpm`, `apps/server/package.json:22-44`). The packages `@ai-sdk/anthropic` and `@ai-sdk/google` are not installed. Each chat `finishReason` comes from the gateway package or from the OpenRouter provider. Media calls (image, video) go through the gateway only. Marketing HTML and the chat brain go through the gateway or through OpenRouter (`apps/server/src/modules/ai-provider/domain/llm-provider.ts:9`, `:75`, `:163`). Higgsfield is a direct MCP call with the OAuth token of the user (`apps/server/src/trigger/run-connector-generation.task.ts:165-203`).

Evidence marks: `file:line` = read in this repo or in `node_modules`. `[URL]` = external document. `[U]` = not verified. Test a `[U]` item in staging before you depend on it.

Vocabulary: this document uses the verb "verify" for all checks. It uses the noun "configuration" for all configuration data. The word "Retry" names the button in the chat banner.

Changes from v2: the four review lenses gave 1 blocker, 22 majors, and 34 minors. All are resolved. Appendix I lists each blocker and major with its resolution.

## A. What happens today

### A.1 Chat stream (`POST /v1/chats/:chatId/ai-stream`)

1. The controller validates the messages, runs `prepareStream`, hijacks the Fastify reply, and gives the raw response to `AiChatService.stream` (`apps/server/src/modules/ai-chat/presentation/http/controllers/ai-chat.controller.ts:122-143`). For a regenerate request, `streamRequestId` is `body.messageId` (`:72-76`).
2. The agent is a `ToolLoopAgent` on `env.AI_CHAT_MODEL` with `stopWhen: isStepCount(12)`. The user selects no model. `ToolLoopAgentSettings` has no `onError` in 7.0.19 (`apps/server/src/modules/ai-chat/agent/chat-agent.ts:428-468`, `apps/server/src/modules/ai-chat/agent/chat-metering.ts:10`, `node_modules/.pnpm/ai@7.0.19_zod@4.4.3/node_modules/ai/dist/index.d.ts:5022`).
3. The abort signal is `AbortSignal.any([clientAbortSignal, AbortSignal.timeout(AI_CHAT_MAX_STREAM_DURATION_MS), leaseLossAbort.signal])`. Lease loss aborts with a reason: `new Error("AI chat execution lease was lost")` or `new Error("AI chat execution lease expired without renewal")` (`apps/server/src/modules/ai-chat/application/services/ai-chat.service.ts:657-665`, `:1267`, `:1281`).
4. Provider and tool failures reach `onAgentStreamError`. This hook queues the gateway-id capture, handles billing, then calls `handleStreamError`. That function calls `Sentry.captureException(error, { tags: { chatId, projectId, userId } })` and `logger.error("AI chat stream failed", error)` (`ai-chat.service.ts:919-963`, `:1415-1439`). `InvalidToolInputError` is a warning branch (`:933-943`). The loop continues.
5. The SDK calls `onError` two times per failure. The first call carries the real error. The second call carries `new Error(chunk.errorText)` from the finish replay (`ai/dist/index.js:7046-7048`). The `streamErrorCaptured` latch keeps only the first call (`ai-chat.service.ts:948-956`).
6. The string sent to the client is fixed: `InvalidToolInputError ? error.message : "An error occurred."` (`ai-chat.service.ts:1442-1445`).
7. The outer `createUIMessageStream.onError` returns the same string (`:1117-1120`). It runs outside `execute`, where `writer` is not in scope. It also receives the synthetic replay error. Setup failures before `writer.merge` are captured and thrown again (`:1099-1115`). Post-hijack failures are captured (`:1188`) because the global filter returns early when `reply.sent` is true (`apps/server/src/infrastructure/http/api-exception.filter.ts:50-52`).
8. When the abort signal fires, `streamText` enqueues `{ type: "abort" }` and closes the stream. No `error` chunk, no `onError` call, and no `finish` event occur (`ai/dist/index.js:8940-8970`). The service has no `onAbort` handler. `streamText` exposes one (`ai/dist/index.d.ts:3644`).
9. Persistence: the assistant row is inserted only when `responseMessage.parts.length > 0` (`:1145-1147`). Continuations upsert (`:1131`). Metadata holds only model, usage, and selected targets (`packages/contracts/src/v1/ai-chat.ts:105-110`, `packages/db/src/schema/chats.ts:65-68`). No finish reason and no error are stored.
10. Turn admission: `turnRequestId` is a hash of `messages.length`, the last message id, and the `type` plus `state` of each part (`:2399-2402`). This is why tool-state changes (approvals, autostart) get a new key today. The operation key is chatId plus requestId (`:294`). A settled turn replayed with the same key is a hard 409 `AI_CHAT_OPERATION_REPLAYED`. `chatReplayConflict()` builds it (`:394-399`) and `admitTurnReservation` throws it (`:462-561`). A provider failure in the middle of a turn still fires `onEnd` with partial usage, so the reservation is settled (`:1017-1046`). An `error` chunk ends the loop (`ai/dist/index.js:9498-9501`, `:5735-5738`).
11. Web: `useChat.onError` verifies only billing. `chatStreamErrorKey` maps each non-409 error to `workspace.chat.errors.stream`. `ChatPane` prints that key two times, gated on `error && !billingError`. It does not use `regenerate`, although the hook returns it (`apps/web/src/features/workspace/lib/use-ai-chat.ts:202-210`, `:271`, `:392-415`, `apps/web/src/features/workspace/components/chat/chat-pane.tsx:342-355`, `packages/internationalization/dictionaries/en/workspace.json:763`). Data parts render only when the renderer lists them (`apps/web/src/features/workspace/components/chat/parts/message-parts.tsx:47-49`).
12. `finishReason: "content-filter"` has no branch on this path. A refused turn with zero parts stores only the user row and shows nothing (`ai-chat.service.ts:999-1031`, `:1145`).
13. The only chat-path classifier lives in the legacy BullMQ worker (`GATEWAY_FORBIDDEN` / `GATEWAY_RATE_LIMITED` / `GENERATION_FAILED`, 300-character truncation). That path is dormant on web (`apps/worker/src/processors/ai-generation.processor.ts:527-538`, `:603-607`, `apps/web/src/features/workspace/lib/ai-chat-context.tsx:24`).

### A.2 Tool errors inside the agent loop

1. A thrown `execute` becomes a `tool-error` part. It goes through `onAgentStreamError` and reaches the client as `tool-output-error` with `errorText: "An error occurred."` (`ai/dist/index.js:7389-7394`). The loop continues to step 12. The Sentry AI integration also captures each thrown tool error with `mechanism.type = "auto.vercelai.channel"` and the tags `vercel.ai.tool.name` / `vercel.ai.tool.callId` (`node_modules/.pnpm/@sentry+server-utils@10.69.0/node_modules/@sentry/server-utils/build/cjs/vercel-ai/vercel-ai-dc-subscriber.js:372-395`). Each tool throw is two Sentry events today.
2. Caught operational problems return `{ status: "unavailable", message }` or `{ status: "queued", attemptId, message }` (`apps/server/src/modules/ai-chat/agent/tools/generate-image.tool.ts:97`, `:349`, `apps/server/src/modules/ai-chat/agent/tools/generate-video.tool.ts:104`, `:319`). A background failure never returns to the model. The durable attempt row and the card carry it (`error` columns: `image-generation-attempts.ts:68`, `media-generation-attempts.ts:112`).
3. The render of `output-error` is not consistent. Video, page, marketing, and leads print `part.errorText`. Image and animation discard it and print fixed copy. Web MCP prints "This step failed.". Native MCP and the native async card print raw `errorText` (`generate-video-part.tsx:226-240`, `generate-image-part.tsx:48-57`, `animate-image-part.tsx:49`, `mcp-tool-part.tsx:912-916`, `apps/native/features/workspace/components/mcp-tool-run.tsx:903-909`, `apps/native/features/workspace/components/async-generation-card.tsx:134-142`).
4. An MCP result with `isError: true` returns to the model as a normal output. The client sees `output-available` and the web renderer marks it "done" (`apps/server/src/modules/mcp-connectors/application/services/mcp-chat-tools.service.ts:1857-1870`, `:2905-2910`, `mcp-tool-part.tsx:1215`).
5. Inside the page builder, image and video failures return `{ message, status }`. `toModelOutput` renders `failed: <message>`. The builder prompt tells the model to fall back to CSS/SVG art (`apps/server/src/modules/ai-chat/agent/site-builder/site-builder-agent.ts:629`, `:1041`, `:1082`, `apps/server/src/modules/ai-chat/agent/site-builder/builder-prompt.ts:44-45`).

1. Provider path: each adapter imports `experimental_generateVideo` and builds `gateway.video(modelId)`. The call is one long `POST /video-model` SSE request. ### A.9 Diagnosis

Zack cannot tell whose fault an error is. Four causes stack:

1. No classification on the chat path. One string covers a gateway 429, an Anthropic 529, a refusal, a `TypeError` in our tool, and a dropped socket (`ai-chat.service.ts:1442-1445`).
2. No provider identity. Sentry captures carry `chatId/projectId/userId` and nothing more (`:1433`). The observability probe found 39 capture sites, none with `provider` or `model`. Gateway requests carry only `op:` and `ws:` tags (`gateway-metering.ts:179-182`).
3. No persisted reason. A failed chat turn writes no assistant row. Media rows store a fixed sentence. Product, edit, and extension runners and the connector task never capture to Sentry. At best, the provider text lives in a Sentry message without class or stack.
4. Sentry blind spots. `vercelAIIntegration` runs only in the Nest API (`packages/observability/src/nestjs.ts:46`). Trigger is errors-only. `logger.error("msg", err)` mirrors only `"msg"`. No AI call has a `functionId` or a conversation id.

The page builder shows the fix. `classifyBuildFailure` plus `failureCode` plus a copy table plus a retry route gives honest, attributed errors today. The job is to apply that pattern to each surface. Add the identity fields that are absent. Use the correct SDK detection rules (section B) and the safety rules of the connector code (section C.4).

## B. Error taxonomy

`AiErrorKind` is a closed enum with sixteen values. Detection uses this order: SDK class (`isInstance`), the `cause` of the error, HTTP status, gateway or OpenRouter `type` / `code`, body fields, provider status strings. Never match strings first. Retryable = the user can start the same request again with the same input, and the failed hold was refunded or settled at zero.

Sources: `ours` | `gateway` | `openrouter` | `provider:<slug>` (`anthropic`, `openai`, `google`, `klingai`, `bytedance`, `xai`, and more) | `higgsfield` | `unknown`.

Visibility policy: `generic` = one neutral sentence, no detail. `category` = the sentence of the kind, with the provider name when known. `forward` = the category sentence plus sanitized provider text on an attribution line (C.4).

Provider label fallback: when `providerLabel` is null, the copy uses `t("workspace.chat.aiError.providerFallback")` = "The AI provider" (en/fr/ar). No sentence renders a null.

All chat and media calls run through the gateway. The gateway error body is `{ error: { message, type, param, code }, generationId }` (`gateway/dist/index.js:468-477`). A `retry-after` header on that response belongs to the gateway, not to the upstream provider. Each rule below that names an upstream code (Anthropic, Google, Kling, Seedance) reads the gateway body `error.code` / `error.message` that carries the upstream value. These sub-rules are [U] until PR0 records a real body. Kling documents were not reachable (HTTP 446 on both official URLs).

### B.1 Rules that follow from the installed packages

1. `GatewayError extends Error`, not `AISDKError`. Use `GatewayError.isInstance` (`gateway/dist/index.d.ts:821-843`). Nine classes are exported: `GatewayError` plus eight concrete classes (authentication, invalid request, rate limit, model not found, internal server, failed dependency, forbidden, response). `GatewayTimeoutError` is defined but not exported (`index.d.ts:1016`, `index.js:2698-2706`). Detect it by `type` / `name` / `statusCode`, never by import.
2. The gateway picks the class from the body field `error.type`, not from the HTTP status. An unknown type at any status becomes `GatewayInternalServerError` with the real `statusCode` (`index.js:368-464`). A non-`APICallError` (fetch `TypeError`, `ECONNRESET`, a DOMException abort) becomes `GatewayResponseError` with `statusCode: 500`, `type: "response_error"`, `response = {}`, and the original error as `cause` (`:580-587`, `:373-389`). An error body the gateway cannot parse (HTML 502/503 from a CDN) is also `GatewayResponseError`, with the real status. Inside a gateway error: read `cause` first, then `statusCode`, then the class. The `response_error` → `provider_error` branch runs only after the `cause` tests. Reuse `e.isRetryable` (408/409/429/>=500, `:73-93`) as the default `retryable` value.
3. Each `GatewayError.message` ends with ` [gen_…]` when a generation id exists (`index.js:84`). Read the id from `e.generationId`. The sanitizer strips a trailing `[gen_[A-Za-z0-9]+]`.
4. `RetryError` wraps an error only after two or more attempts, with reason `maxRetriesExceeded` or `errorNotRetryable` (`provider-utils/dist/index.js:3114-3151`). Video calls use `maxRetries: 0`, so they never see it. Classify by `lastError`. Keep `retryable: true` for `maxRetriesExceeded`.
5. OpenRouter one-shot and stream-start failures are `APICallError` with the parsed body on `.data` (`openrouter/dist/index.js:2389-2435`, `:2556-2563`). The `APICallError` copy of the provider shares the `vercel.ai.error.AI_APICallError` symbol, so `APICallError.isInstance` from `ai` matches (`:76-81`). Mid-stream failures are not `APICallError`. The provider enqueues `{ type: "error", error: value.error }` with the raw SSE object (`:3944-3953`, `:4264-4267`). Moderation errors occur before any token is sent, so they are stream-start only. The mid-stream `error.metadata` shape is `{ error_type: string, provider_code?: string }` [https://openrouter.ai/docs/api-reference/errors]. The classifier has a branch for that plain object when `context.route === "openrouter"`.
6. The gateway keeps per-attempt provider text and status in `providerMetadata.gateway.routing.modelAttempts[].providerAttempts[]` (`provider`, `credentialType`, `success`, `error`, `statusCode`, `startTime`, `endTime`, `providerApiModelId`, `providerResponseId`). The generation id is in `providerMetadata.gateway.generationId`. In a stream these arrive on `finish-step` parts (`TextStreamFinishStepPart.providerMetadata`, `ai/dist/index.d.ts:3034-3042`), not on `finish` (`:3046-3051`). The repo reads the id only from step `providerMetadata` (`llm-provider.ts` comment above `withOpenRouterGenerationId`, `gateway-metering.ts:129-159`). A generation id on the first content chunk is [U] for the AI SDK stream protocol. [https://vercel.com/docs/ai-gateway/models-and-providers/provider-filtering-and-ordering, https://vercel.com/docs/ai-gateway/models-and-providers/model-fallbacks]
7. This repo cannot show if the gateway maps an Anthropic `refusal` to `content-filter` or to `other`. PR0 (section G) settles it with one real call. Until then the classifier accepts both shapes and always logs `rawFinishReason`. On the OpenRouter route the provider maps the normalized `finish_reason` and sets `raw` to that value. It never reads `native_finish_reason` (`openrouter/dist/index.js:2705-2725`). Native refusal text is not available on that route.
8. `finishReason: "content-filter"` on HTTP 200 is not an error to the SDK. `classifyFinish` (C.2) handles it, not `onError`.
9. The video model turns an SSE `error` event into `APICallError({ message: event.message, statusCode: event.statusCode, responseBody: JSON.stringify(event), data: { error: { message, type: event.errorType, param } } })` (`gateway/dist/index.js:1497-1516`). Then `asGatewayError` picks the class from `data.error.type` (`:1553-1556`, `:368-464`). The event schema has only `message`, `errorType`, `statusCode`, `param` (`:1620-1627`). No numeric Kling code and no Seedance `error.code` field exist on this path. Provider codes reach the app only inside `message` or `param`. `NoVideoGeneratedError` is thrown only when a successful result has zero videos (`ai/dist/index.js:13624`).
10. `doStream` on the gateway route forwards each parsed stream part unchanged. This includes `{ type: "error", error }` parts from the gateway SSE (`gateway/dist/index.js:1040-1052`). `asGatewayError` wraps only the thrown pre-stream failure (`:1059-1063`). A provider failure after the first token reaches `onAgentStreamError` as the plain value from the gateway `error` part. The shape is [U]. PR0 records one by a forced mid-stream failure.
11. The image model `doGenerate` catch throws `asGatewayError(error)` (`gateway/dist/index.js:1189-1193`). An OpenAI moderation 400 is therefore a `GatewayError` subclass with `cause` = `APICallError`. `APICallError.isInstance` at the top level is false. The provider slug comes from the model id prefix (`openai/gpt-image-2`) or from routing metadata, not from a URL host.

### C.3 Detection order inside `classifyAiError`

1. Abort. If `context.abortSignal.reason` is a `TimeoutError` → `timeout`, source `ours`, key `errors.ai.timeout_budget`. If the reason is an `Error` whose message starts with `"AI chat execution lease"` (`ai-chat.service.ts:1267`, `:1281`) → `internal`. If `abortSignal.reason?.name === "AbortError"` or `abortSignal.aborted` is true → `cancelled`. Do not read `error.name`: a wrapped abort is a `GatewayResponseError` (B.1 rule 2). If routing metadata is present on a failed stream is [U] (PR0 records it).

- `finishReason === "length"` → `null`. The card shows the partial text.
- All other cases → `null`.

### C.4 Sanitization for forwarded provider text

`sanitizeProviderText` runs only for `content_moderated`, `connector_rejected`, and `connector_account`. Steps:

1. If the text parses as JSON, take `error.message` / `message` / `task_status_msg` / `detail` / the first `content[].text`, in that order. If none of those keys exists, return null. Never take the first line of a JSON payload: a Higgsfield status blob carries the prompt, ids, and internal URLs. If the text is not JSON, take the first non-empty line.
2. Strip request ids: `stripRequestIds` plus a trailing `[gen_[A-Za-z0-9]+]`.
3. Drop each URL of any scheme (`\b[a-z][a-z0-9+.-]*:\/\/\S+`), `host:port` pairs, and emails.
4. Drop each token that `looksLikeCredential` matches. Extend that function with the `ya29.` and `EAA` prefixes, `Bearer `, `access_token=`, `refresh_token=`.
5. Drop lines that start with `at ` or contain `node_modules/`.
6. Drop `Support codes: …` suffixes (Veo).
7. Collapse whitespace.
8. Cap at 240 characters with `…`.
9. Return `null` if fewer than 4 characters remain.

Per-kind allowlist for `content_moderated`:

| Provider | Rule |
|---|---|
| OpenAI images | Do not forward `error.message`. Build `params.text` from `moderation_details.categories` ("sexual, violence"). |
| OpenRouter (stream start 403) | Forward `metadata.reasons[]` through an enum filter of known category words only. Never read `flagged_input`: it echoes the prompt. Render "Reason given: {text}". |
| Seedance | Forward the message (neutral). |
| Kling | Forward the message only when it carries code `1301` [U]. For other risk-control text, log it and show the category sentence. |
| Veo | Never forward. Category sentence plus "This often happens with real people or faces." |
| Higgsfield `nsfw` | The fixed documented sentence. |

`connector_rejected`: forward free text only from an explicit per-connector allowlist. Today that is the Higgsfield `validationMessage` table (`provider-rejection.ts:55-62`). For `meta-ads`, `tiktok-ads`, and unknown connectors, use the category sentence only. This matches `sanitizeConnectorOperationError` (`connector-operation-error.ts:10-22`). `connector_account`: forward the two current fixed sentences only (`provider-rejection.ts:23-35`). Fixture (PR1): a Higgsfield status JSON with `request_id`, a `ya29.` token, and an image URL → the sanitizer returns `null`.

The same redaction (steps 3-5) runs on `raw.responseBody`, on each `providerAttempts[].error` string, and on the `ai.call.failed` log attributes before they enter Sentry. Provider error bodies echo prompt fragments (OpenRouter `flagged_input`, research-gateway-openrouter.md:254).

### C.5 Transport per surface

**(1) Chat stream: `data-ai-error` part, after the billing precedent.** The precedent: the contract discriminated union `aiChatBillingErrorDataSchema` (`packages/contracts/src/v1/ai-chat.ts:39-50`), registered in `AiChatDataParts` (`:74-77`), written once per turn by `writeBillingError` (`ai-chat.service.ts:902-915`), suppressed as `tool-error` and made terminal by `stopOnBillingError` (`:966-987`), registered on the client in `dataPartSchemas` (`use-ai-chat.ts:186-189`), and dispatched in `onData` (`:212-222`). The new part mirrors it:

- Contract: `AiChatDataParts["ai-error"]: AiErrorData`. Wire type `data-ai-error`. Data parts support `transient` and id reconciliation (`ai/dist/index.d.ts:2373`, `:2398`).
- Server: the `writer` is hoisted into a closure variable set at the start of `execute`. The outer `onError` (`:1117-1120`) and the setup catch (`:1099-1115`) can then reach it. `createUIMessageStream` evaluates `onError(error)` before `safeEnqueue({ type: "error", errorText })` in all three catch paths (`ai/dist/index.js:10190-10222`). A part written through the hoisted writer inside `onError` is therefore enqueued before the `error` chunk. The G.2 spec keeps this as a test.
- `onAgentStreamError` (`:919`) becomes: `const n = classifyAiError(error, ctx)` then `if (n) writeAiError(n, toolCallId?)`, then it returns the masked string `"An error occurred."`. It returns the masked string for warning classes too. Today `InvalidToolInputError` returns `error.message`, which embeds the full JSON of the tool input of the model (`ai/dist/index.js:152-158`). That text can echo prompt text, URLs, and MCP arguments. The `invalidToolInputTexts` set (`:944-946`) is then not necessary. Warning classes (C.3 step 10) return before `writeAiError`.
- One write per failure: the SDK calls `onError` two times (A.1.5). `writeAiError` runs only on the first call. Reuse the `streamErrorCaptured` latch, or skip when `error.message === "An error occurred."` and the latch is set. Without this rule the id-reconciled terminal part is overwritten by an `unknown` classification of the synthetic `Error`. The outer `onError` also receives the replay after the stream is closing, so the hoisted `writer` can be closed there. Guard the write with `writerClosed`.
- `onAbort` (new, `streamText` / agent option, `ai/dist/index.d.ts:3644`): an abort emits no `error` chunk, no `onError`, and no `finish` (A.1.8). - `writeAiError` writes at most one terminal part per turn (`id: "ai-error"`, reconciled in place) and any number of tool-scoped parts (`id: "ai-error:<toolCallId>"`). Terminal parts are not transient. They land in `responseMessage.parts`, `parts.length > 0` becomes true, and a failed turn persists an assistant row that holds the error part (fixes A.8 #2). `connector_unreachable` is written as a transient part with `terminal: false` at stream start and is never stored.

If PR0 shows an id on the `response-metadata` part, read it there too. Do not promise coverage of a dropped connection before PR0 records a stream. On `finish`, add `finishReason`, `rawFinishReason`, `provider`, `gatewayGenerationId`. On `finish`, `classifyFinish` can write a terminal `content_moderated` part.
- Tool-scoped: the transform (`:966`) gains a branch: `part.type === "tool-error" && !billing` → write `data-ai-error` with `toolCallId`, then `controller.enqueue(part)` unchanged. The SDK still emits `tool-output-error` and the model still sees the failure.
